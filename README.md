# subs-resolver

Лёгкий HTTP-сервис на TypeScript: получает список доменов в URL, последовательно запрашивает подписку и возвращает первый успешный ответ. Список доменов меняется без перезапуска. VPN-трафик через сервис не проходит.

## Развёртывание одной командой

Нужен сервер **Ubuntu 24.04 с systemd** и пользователь с sudo. До установки создай DNS-запись `A` для домена, указывающую на публичный IP сервера. Если есть `AAAA`, она тоже должна указывать на доступный IPv6 этого сервера. В firewall провайдера разреши входящие TCP **80/443** и свой SSH-порт.

Подключись к серверу по SSH, замени `subs.example.com` своим доменом и выполни одну строку:

```sh
sudo apt-get update && sudo apt-get install -y curl ca-certificates && curl -fsSL https://raw.githubusercontent.com/Dmitriy129/subs-resolver/main/scripts/deploy.sh | sudo bash -s -- --domain subs.example.com
```

Если curl уже установлен:

```sh
curl -fsSL https://raw.githubusercontent.com/Dmitriy129/subs-resolver/main/scripts/deploy.sh | sudo bash -s -- --domain subs.example.com
```

Команды выполняются **на сервере**, а не на твоём рабочем компьютере. Скрипт не задаёт вопросов о домене: `--domain` обязателен и принимает только имя без схемы, порта и пути.

Установщик:

1. Скачивает репозиторий в `/opt/subs-resolver` и создаёт отдельного пользователя `subs-resolver`.
2. Устанавливает NVM, Node из `.nvmrc`, Corepack и pnpm из `package.json`; устанавливает зависимости и собирает проект.
3. Создаёт `.env` со случайным UUID доступа. При повторной установке сохраняет UUID и настройки.
4. Запускает Node как службу systemd с автозапуском и перезапуском при сбое.
5. Устанавливает Caddy: HTTPS на 443, HTTP на 80, получение публичного сертификата и автоматическое продление.
6. Настраивает UFW и проверяет, что HTTPS отвечает с действительным сертификатом.

В конце скрипт печатает шаблон готового URL подписки. Если DNS или firewall провайдера ещё не готовы, установка завершится ошибкой проверки HTTPS с подсказкой; Caddy продолжит попытки выпуска сертификата. После исправления DNS/доступа команду можно повторить.

Если 80/443/3000 заняты чужим сервисом или конфигурация конфликтует с существующей, установщик останавливается. Он не отключает чужой Nginx, Apache или Caddy и не перезаписывает их конфигурацию. Рассчитан прежде всего на отдельную VPS.

## Как пользоваться

Пример URL, где `<UUID>` — значение, выданное установщиком:

```text
https://subs.example.com/<UUID>/sub/CLIENT_ID?available_domains=vpn-main.example&available_domains=vpn-backup.example&format=base64
```

Резолвер последовательно запросит:

```text
https://vpn-main.example/sub/CLIENT_ID?format=base64
https://vpn-backup.example/sub/CLIENT_ID?format=base64
```

`available_domains` — массив через повторение query-параметра в порядке приоритета. JSON и запись с `[]` не используются. Свой UUID-префикс и все служебные параметры резолвер удаляет; остальные параметры сохраняют порядок, повторы и кодирование.

Домены проверяются простой регуляркой: ASCII-имена с точками, буквами, цифрами и дефисами. Без схемы, порта, IP-адреса или пути; международные домены — в punycode. Запросы к источникам начинаются с HTTPS на 443. Статического списка разрешённых доменов нет.

На резервных доменах должен существовать тот же путь/идентификатор подписки. Разные токены у разных провайдеров сервис не сопоставляет. Каждый запрос начинает перебор с первого домена своего списка.

## Порты и безопасность

`127.0.0.1:3000` — намеренная настройка: Node доступен только Caddy на том же сервере. Для доступа с телефона менять её на `0.0.0.0` не нужно. Снаружи работает Caddy на стандартном HTTPS-порту **443**, а **80** используется для HTTP и проверки сертификата. Установщик также разрешает UDP 443 для HTTP/3.

UFW получает запрет входящих соединений по умолчанию и разрешение исходящих. Перед включением добавляются разрешения для SSH-портов из конфигурации sshd и действующих соединений/слушателей, а также 80/443. **Существующие правила сохраняются:** установщик не делает `ufw reset` и не закрывает ранее явно разрешённые порты других сервисов. Firewall провайдера он изменить не может.

Других «системных» входящих портов для этого приложения не требуется. DNS и загрузки работают через исходящие соединения. На сервере с другими приложениями проверь их сетевые требования перед установкой UFW.

Поскольку репозиторий публичный, общего секретного UUID в коде нет. Для каждой установки UUID генерируется отдельно и хранится в `/opt/subs-resolver/.env` с правами `0600`, вне Git. Сохрани URL в секрете: знающий его может задавать произвольные домены. Регулярка проверяет только формат имени; фильтрации частных адресов после DNS-разрешения нет.

Приложение не записывает URL и UUID в журнал. Для создаваемого сайта Caddy access-лог не включается. Node работает от отдельного пользователя без root, с ограничениями systemd на запись и доступ к домашним каталогам.

## Настройки и обслуживание

В `.env` находятся:

| Переменная | Значение | Назначение |
| --- | --- | --- |
| `ACCESS_ID` | Случайный UUID v4 | Секретный префикс маршрута |
| `HOST` | `127.0.0.1` | Адрес Node |
| `PORT` | `3000` | Порт Node |
| `REQUEST_TIMEOUT_MS` | `5000` | Таймаут одной попытки, включая загрузку ответа; максимум 60000 |

Служба принудительно задаёт `HOST=127.0.0.1` и `PORT=3000`, чтобы адрес совпадал с Caddy, даже если в старой `.env` были другие значения. Изменение UUID или таймаута требует перезапуска службы; изменение доменов в URL — нет.

```sh
sudo systemctl status subs-resolver caddy
sudo journalctl -u subs-resolver -n 50
sudo journalctl -u caddy -n 50
sudo ufw status numbered
```

Чтобы обновить код, повтори ту же команду развёртывания с `--domain`. Установщик выполнит `git pull --ff-only`, пересоберёт проект, обновит путь Node в службе и перезапустит её. UUID сохраняется. При ручных изменениях отслеживаемых файлов обновление остановится, ничего не отбрасывая.

Сборка очищает только `dist`, поэтому старые скомпилированные файлы не остаются. Конфигурация Caddy для проекта хранится в `/etc/caddy/sites/subs-resolver.caddy`; её подключение добавляется в основной Caddyfile. Сертификаты и их продление обслуживает Caddy — отдельный cron или Certbot не нужен.

## Поведение при ошибках

- Неизвестный UUID/путь — `404`; метод кроме GET — `405`. После UUID нужен `/`.
- Отсутствующий, пустой или неправильный `available_domains` — `400` без обращения к источникам.
- Успех — HTTP `200` с непустым телом до 2 MiB после распаковки.
- Сетевая ошибка, другой статус, таймаут, пустой, оборванный или слишком большой ответ — переход к следующему домену.
- Тело полностью читается перед отправкой; частично загруженная подписка не выдаётся.
- При отказе всех источников — `503`. Кеширования и фоновых проверок нет.
- Передаются клиентские `User-Agent`/`Accept` и основные заголовки подписки. Отключение клиента отменяет загрузку.

Ожидание при нескольких отказах может достигать `число доменов × REQUEST_TIMEOUT_MS`. Подписки не проверяются на работоспособность самого VPN: непустая HTML-страница с `200` тоже считается успехом. Автоматическое переключение зависит от мобильного приложения.

## Разработка и проверки

Зафиксированы Node **24.22.3** (`.nvmrc`), pnpm **10.34.9** (`package.json`), NVM **0.41.0** для новой установки и Corepack **0.36.0** (`scripts/install.sh`). Зависимостей при запуске приложения нет; TypeScript и типы Node используются при сборке.

Для ручной установки в уже клонированном каталоге на Ubuntu есть `bash scripts/install.sh`: он устанавливает окружение и собирает проект, но не создаёт systemd/Caddy/UFW. Полное развёртывание выполняет `scripts/deploy.sh`.

```sh
pnpm install --frozen-lockfile
pnpm run setup
pnpm build
pnpm test
pnpm start
```

Тесты проверяют перебор, маршруты, параметры, таймауты, обрывы, gzip, ограничения тела, отмену запросов, независимые UUID, создание/миграцию `.env` и сохранение секрета при повторном setup. Сетевые тесты используют локальные тестовые HTTP-серверы без реальных подписок.

[GitHub Actions](https://github.com/Dmitriy129/subs-resolver/actions) выполняет установку окружения с нуля и тесты на Ubuntu 24.04. Это не проверяет выпуск настоящего сертификата для твоего домена и правила firewall твоей VPS — их проверяет установщик при развёртывании.

Документация: [Caddy и автоматический HTTPS](https://caddyserver.com/docs/automatic-https), [установка Caddy](https://caddyserver.com/docs/install#debian-ubuntu-raspbian), [UFW](https://manpages.ubuntu.com/manpages/noble/man8/ufw.8.html).
