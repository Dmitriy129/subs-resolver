# subs-resolver

Лёгкий HTTP-сервис на TypeScript: получает полные URL подписок, проверяет их группами до 10 параллельных запросов и возвращает временный редирект `302` на первый доступный источник по заданному приоритету. Результаты проверок доступности кешируются на 5 минут. Подписку клиент загружает напрямую с выбранного сервиса. Список подписок меняется без перезапуска. VPN-трафик через сервис не проходит.

## Развёртывание одной командой

Нужен сервер **Ubuntu 24.04 или Debian 13 с systemd** и пользователь с sudo. Используется один общий установщик: он определяет ОС через `/etc/os-release`. На минимальном Debian без sudo выполняй команды от root, убрав из них `sudo`. До установки создай DNS-запись `A` для домена, указывающую на публичный IP сервера. Если есть `AAAA`, она тоже должна указывать на доступный IPv6 этого сервера. В firewall провайдера разреши входящие TCP **80/443** и свой SSH-порт.

Подключись к серверу по SSH, замени `subs.example.com` своим доменом и выполни одну строку:

```sh
sudo apt-get update && sudo apt-get install -y curl ca-certificates && curl -fsSL https://raw.githubusercontent.com/Dmitriy129/subs-resolver/main/scripts/deploy.sh | sudo bash -s -- --domain subs.example.com
```

Если curl уже установлен:

```sh
curl -fsSL https://raw.githubusercontent.com/Dmitriy129/subs-resolver/main/scripts/deploy.sh | sudo bash -s -- --domain subs.example.com
```

Команды выполняются **на сервере**, а не на твоём рабочем компьютере. Скрипт не задаёт вопросов о домене: `--domain` обязателен и принимает только имя без схемы, порта и пути.

Установщик:

1. Скачивает репозиторий в `/opt/subs-resolver` и создаёт отдельного пользователя `subs-resolver`.
2. Устанавливает NVM, Node из `.nvmrc`, Corepack и pnpm из `package.json`; устанавливает зависимости и собирает проект.
3. Создаёт `.env` со случайным UUID доступа. При повторной установке сохраняет UUID и настройки.
4. Запускает Node как службу systemd с автозапуском и перезапуском при сбое.
5. Устанавливает Caddy: HTTPS на 443, HTTP на 80, получение публичного сертификата и автоматическое продление.
6. Настраивает UFW и проверяет, что HTTPS отвечает с действительным сертификатом.

В конце скрипт печатает шаблон готового URL подписки. Если DNS или firewall провайдера ещё не готовы, установка завершится ошибкой проверки HTTPS с подсказкой; Caddy продолжит попытки выпуска сертификата. После исправления DNS/доступа команду можно повторить.

Если 80/443/3000 заняты чужим сервисом или конфигурация конфликтует с существующей, установщик останавливается. Он не отключает чужой Nginx, Apache или Caddy и не перезаписывает их конфигурацию. Рассчитан прежде всего на отдельную VPS.

## Как пользоваться

Открой `https://subs.example.com/<UUID>/` без query-параметров — это страница сборки ссылки. Вставь полные URL подписок по порядку приоритета: основной первым, резервные ниже. Строки можно добавлять и удалять. Нажми «Собрать ссылку» и скопируй результат в приложение.

Домен и UUID берутся из адреса страницы. Генерация происходит в браузере: введённые ссылки не отправляются на сервер и не сохраняются между открытиями страницы. Готовая ссылка использует тот же адрес с повторяющимися параметрами `subs`. Запрос с `subs` работает как раньше — проверяет источники и перенаправляет к первому доступному.

Интерфейс состоит из `public/index.html` и `public/index.js`, без дополнительных библиотек и сборки. Они поставляются вместе с проектом и доступны только по маршрутам с UUID. Обычная команда обновления устанавливает и страницу.

Пример URL, где `<UUID>` — значение, выданное установщиком:

```text
https://subs.example.com/<UUID>/?subs=https%3A%2F%2Fvpn-main.example%2Fsub%2FCLIENT_ID%3Fformat%3Dbase64&subs=https%3A%2F%2Fvpn-backup.example%2Fsubscription%2FBACKUP_ID
```

Оба URL попадут в первую группу; при отсутствии действующего кеша они будут проверены одновременно:

```text
https://vpn-main.example/sub/CLIENT_ID?format=base64
https://vpn-backup.example/subscription/BACKUP_ID
```

Список разбивается на последовательные группы: URL 1–10, затем 11–20 и так далее. Для каждого URL резолвер использует действующий результат из кеша или запускает новую проверку. Новые проверки группы выполняются параллельно; резолвер ждёт завершения каждой, включая чтение тела или таймаут. Затем выбирает первый успешный URL в исходном порядке списка. Если успешных нет, начинает следующую группу; если есть — остальные группы не проверяет.

Даже если основной источник ответил быстро или уже отмечен доступным в кеше, ответ клиенту ждёт остальные новые проверки текущей группы. Каждый URL этой группы получает результат из кеша или новой проверки, поэтому без кеша запросов к источникам может быть больше, чем при прежнем последовательном переборе. Размер группы фиксирован — максимум 10 одновременных новых проверок на один входящий запрос, а не общий лимит сервера; дополнительных настроек не требуется.

После выбора доступного источника по новой проверке или кешу ответ резолвера содержит `302 Found`, заголовок `Location` с выбранным URL и `Cache-Control: no-store`; тело ответа пустое. В `Location` используется URL из `subs` в стандартной URL-форме, с кодированием не-ASCII символов. Если сам источник перенаправляет проверочный запрос, резолвер проверяет конечный ответ, но в своём редиректе сохраняет исходный выбранный URL.

`subs` — массив через повторение query-параметра в порядке приоритета. Каждый элемент — полный URL, закодированный через `encodeURIComponent` или `URLSearchParams`. JSON и запись с `[]` не используются. Сервис декодирует внешний query один раз и передаёт полученный URL в `fetch`, без склейки доменов и путей. Другие параметры внешнего URL источнику не передаются.

Разрешены абсолютные HTTP(S)-адреса, включая собственные порты, IP-адреса, пути и query-параметры. Логин/пароль в URL, фрагменты `#...` и неэкранированные пробелы не поддерживаются. Статического списка разрешённых источников нет.

Основная и резервная подписки могут иметь разные домены, пути, идентификаторы и параметры. Каждый запрос начинает выбор с первой группы своего списка, используя кеш, если он есть; порядок URL задаёт приоритет, а скорость ответа его не меняет. Поддерживаются `/<UUID>/` и `/<UUID>`; путь подписки указывается только внутри `subs`.

Чтобы не кодировать вложенные `?`, `&` и `%` вручную, запрос можно собрать так. `-i` покажет статус `302` и заголовок `Location` без перехода по нему:

```sh
curl -i --get 'https://subs.example.com/<UUID>/' \
  --data-urlencode 'subs=https://vpn-main.example/sub/CLIENT_ID?format=base64&group=mobile' \
  --data-urlencode 'subs=https://vpn-backup.example:8443/another/BACKUP_ID'
```

Чтобы перейти по редиректу и увидеть саму подписку, используй `-L`:

```sh
curl -sS -L --get 'https://subs.example.com/<UUID>/' \
  --data-urlencode 'subs=https://vpn-main.example/sub/CLIENT_ID?format=base64&group=mobile' \
  --data-urlencode 'subs=https://vpn-backup.example:8443/another/BACKUP_ID'
```

Мобильное приложение должно поддерживать HTTP-редиректы и сохранять стабильный URL резолвера для следующих обновлений. Поддержку такого поведения в VituraNG нужно проверить в самом приложении. После редиректа источник должен быть доступен с телефона: успешная проверка с VPS не гарантирует доступность в мобильной сети. Если источник недоступен уже клиенту, резолвер об этом не узнает и другой URL в рамках этого обновления не выберет.

При новой проверке резолвер полностью загружает ответ источника, затем клиент загружает подписку ещё раз напрямую. Попадание в кеш исключает эту проверочную загрузку на VPS. Заголовки подписки, включая лимиты и интервал обновления, клиент получает от самого источника.

Старый формат с `available_domains` и путём после UUID больше не поддерживается. После обновления сервиса нужно заменить URL в клиенте на новый формат.

## Кеш проверок

Кеш хранит только признак доступности (`true` или `false`) на **5 минут после завершения проверки**, без тела подписки. Ключ — полный URL в стандартной URL-форме и входящие `User-Agent`/`Accept`: ответы для браузера и приложения могут различаться. В памяти процесса хранится до **1000 записей**; при заполнении удаляется самая старая. На диск ничего не записывается, перезапуск очищает кеш, фоновых проверок нет. Заголовок ответа `Cache-Control: no-store` запрещает клиенту кешировать редирект и не отключает этот внутренний кеш.

Кешируются и успешные проверки, и реальные отказы: HTTP-ошибки, проблемы DNS/TCP/TLS, таймауты, пустые, слишком большие или оборванные тела. Отмена проверки из-за отключения клиента не записывается как недоступность. Состояние источника может измениться до истечения записи: восстановленный основной источник будет проверен заново при следующем запросе после истечения кеша.

Чтобы принудительно проверить источники сейчас, добавь **`&no_cache=1`** к готовой ссылке. Параметр пропускает чтение кеша для этого запроса, но свежие результаты обновляют соответствующие записи; весь кеш не очищается. Внешний `no_cache` источникам не передаётся. Существующие ссылки без него автоматически используют кеш.

```sh
curl -i --get 'https://subs.example.com/<UUID>/' \
  --data-urlencode 'subs=https://vpn-main.example/sub/CLIENT_ID' \
  --data-urlencode 'no_cache=1'
```

## Порты и безопасность

`127.0.0.1:3000` — намеренная настройка: Node доступен только Caddy на том же сервере. Для доступа с телефона менять её на `0.0.0.0` не нужно. Снаружи работает Caddy на стандартном HTTPS-порту **443**, а **80** используется для HTTP и проверки сертификата. Установщик также разрешает UDP 443 для HTTP/3.

UFW получает запрет входящих соединений по умолчанию и разрешение исходящих. Перед включением добавляются разрешения для SSH-портов из конфигурации sshd и действующих соединений/слушателей, а также 80/443. **Существующие правила сохраняются:** установщик не делает `ufw reset` и не закрывает ранее явно разрешённые порты других сервисов. Firewall провайдера он изменить не может.

Других «системных» входящих портов для этого приложения не требуется. DNS и загрузки работают через исходящие соединения. На сервере с другими приложениями проверь их сетевые требования перед установкой UFW.

Поскольку репозиторий публичный, общего секретного UUID в коде нет. Для каждой установки UUID генерируется отдельно и хранится в `/opt/subs-resolver/.env` с правами `0600`, вне Git. Сохрани URL в секрете: знающий его может задавать произвольные HTTP(S)-адреса. Фильтрации частных IP-адресов нет.

Приложение не записывает URL и UUID в журнал. Для создаваемого сайта Caddy access-лог не включается. Node работает от отдельного пользователя без root, с ограничениями systemd на запись и доступ к домашним каталогам.

## Настройки и обслуживание

В `.env` находятся:

| Переменная | Значение | Назначение |
| --- | --- | --- |
| `ACCESS_ID` | Случайный UUID v4 | Секретный префикс маршрута |
| `HOST` | `127.0.0.1` | Адрес Node |
| `PORT` | `3000` | Порт Node |
| `REQUEST_TIMEOUT_MS` | `5000` | Общий таймаут одной попытки: DNS, TCP/TLS, редиректы и загрузка ответа; максимум 60000 |

Служба принудительно задаёт `HOST=127.0.0.1` и `PORT=3000`, чтобы адрес совпадал с Caddy, даже если в старой `.env` были другие значения. Изменение UUID или таймаута требует перезапуска службы; изменение подписок в URL — нет.

```sh
sudo systemctl status subs-resolver caddy
sudo journalctl -u subs-resolver -n 50
sudo journalctl -u caddy -n 50
sudo ufw status numbered
```

Если соединение с источником медленное, можно увеличить `REQUEST_TIMEOUT_MS` в `/opt/subs-resolver/.env`, например до `20000`, и выполнить `sudo systemctl restart subs-resolver`. Этот предел применяется и к установлению соединения: отдельного ограничения в 10 секунд нет. Проверка сертификатов остаётся включённой.

При отказе журнал показывает номер источника, код причины и время попытки. Например, `UND_ERR_CONNECT_TIMEOUT` означает таймаут подключения, `TimeoutError` — исчерпание общего времени попытки, `HTTP_STATUS` с полем `status` — неуспешный HTTP-статус источника. Адреса, query-параметры и содержимое подписок в журнал не записываются.

Чтобы обновить установленную версию из `main`, повтори ту же команду развёртывания с `--domain`. Установщик выполнит `git pull --ff-only`, пересоберёт проект, обновит путь Node в службе и перезапустит её. UUID сохраняется. Если на сервере ранее была выбрана `redirector`, установщик вернёт её на `main`, только если все её коммиты уже включены в `main`. При ручных изменениях отслеживаемых файлов обновление остановится, ничего не отбрасывая.

Сборка очищает только `dist`, поэтому старые скомпилированные файлы не остаются. Конфигурация Caddy для проекта хранится в `/etc/caddy/sites/subs-resolver.caddy`; её подключение добавляется в основной Caddyfile. Сертификаты и их продление обслуживает Caddy — отдельный cron или Certbot не нужен.

## Поведение при ошибках

- Неизвестный UUID/путь — `404`; метод кроме GET — `405`. Подписки запрашиваются по UUID с завершающим `/` или без него; скрипт страницы доступен по `/<UUID>/index.js`.
- `/<UUID>/` без query-параметров — страница сборки ссылки; `/<UUID>` без параметров перенаправляет на неё.
- Непустой query без `subs`, пустой или неправильный `subs` — `400` без обращения к источникам.
- Источник считается доступным, если конечный ответ после его редиректов — HTTP `200` с полностью загруженным непустым телом до 2 MiB после распаковки.
- После выбора по новым или кешированным результатам клиент получает HTTP `302`, `Location` выбранного источника и пустое тело. Ответы источника и его заголовки через резолвер не передаются.
- Сетевая ошибка, другой статус, таймаут, пустой, оборванный или слишком большой ответ — неуспешная проверка этого источника. После завершения группы выбирается первый успешный URL; следующая группа запускается только при отказе всей текущей.
- Редирект выдаётся после получения результатов для всей группы, включая завершение новых проверок. Для новой успешной проверки требуется прочитать всё тело; успешных HTTP-заголовков недостаточно.
- Если все источники недоступны по новым или кешированным результатам — `503`. Фоновых проверок нет; редирект отправляется с `Cache-Control: no-store`.
- При проверке источника передаются клиентские `User-Agent`/`Accept`. Отключение клиента отменяет все активные проверки группы без записи их как отказов в кеш; следующая группа не запускается.

При отсутствии действующего кеша или с `no_cache=1` ожидание проверок в худшем случае составляет примерно `ceil(число URL / 10) × REQUEST_TIMEOUT_MS`, плюс накладные расходы. Например, для 10 URL с таймаутом 20 секунд одна группа ждёт примерно до 20 секунд вместо суммы до 200 секунд. Попадания в кеш не требуют сетевого ожидания. Подписки не проверяются на работоспособность самого VPN: непустая HTML-страница с `200` тоже считается успехом. Автоматическое переключение зависит от мобильного приложения.

## Разработка и проверки

Зафиксированы Node **24.22.3** (`.nvmrc`), pnpm **10.34.9** (`package.json`), NVM **0.41.0** для новой установки и Corepack **0.36.0** (`scripts/install.sh`). Единственная зависимость при запуске — **Undici 7.30.1**, HTTP-клиент без дополнительных зависимостей: он позволяет согласовать таймаут подключения с общим таймаутом запроса. TypeScript и типы Node используются при сборке.

Для ручной установки в уже клонированном каталоге на Ubuntu или Debian есть `bash scripts/install.sh`: он устанавливает окружение и собирает проект, но не создаёт systemd/Caddy/UFW. Полное развёртывание выполняет общий `scripts/deploy.sh`.

```sh
pnpm install --frozen-lockfile
pnpm run setup
pnpm build
pnpm test
pnpm start
```

Тесты проверяют параллельные группы и их границы, сохранение приоритета источников, кеширование и его обход, выбор редиректа, переход клиента к подписке, маршруты, параметры, таймауты, обрывы, gzip, ограничения тела, отмену активной группы, независимые UUID, создание/миграцию `.env` и сохранение секрета при повторном setup. Сетевые тесты используют локальные тестовые HTTP-серверы без реальных подписок.

[GitHub Actions](https://github.com/Dmitriy129/subs-resolver/actions) выполняет установку окружения с нуля, сборку и тесты на Ubuntu 24.04 и в контейнере Debian 13. Полное развёртывание systemd/Caddy/UFW в контейнере не проверяется. Выпуск настоящего сертификата и доступность HTTPS проверяет установщик на VPS.

Документация: [Caddy и автоматический HTTPS](https://caddyserver.com/docs/automatic-https), [установка Caddy](https://caddyserver.com/docs/install#debian-ubuntu-raspbian), [UFW](https://manpages.ubuntu.com/manpages/noble/man8/ufw.8.html).

## Короткие ссылки и резервная копия

На странице `https://ваш-домен/<ACCESS_ID>/` доступны две формы:

- **Подписки**: соберите fallback-ссылку и нажмите «Создать короткую ссылку». Адрес передаётся между формами в памяти браузера, без query-параметров и перезагрузки.
- **Короткие ссылки**: введите имя (например `ABC`) или сгенерируйте случайное из 10 символов, затем нажмите «Проверить». Свободное имя открывает создание, занятое — редактирование с сохранённым адресом. Создание не перезаписывает занятое имя, даже если другой запрос успел занять его после проверки.
- **Перенос данных**: отдельная страница со скачиванием и загрузкой JSON, доступная с основной страницы.

Публичный адрес `https://ваш-домен/s/ABC` отвечает временным редиректом 302 на сохранённый HTTP(S)-адрес. После редактирования короткий адрес остаётся прежним. Если назначение — fallback-ссылка, браузер или приложение проходит обычную цепочку редиректов. Доступ к управлению и выгрузке закрыт вашим `ACCESS_ID`; не публикуйте адрес страницы управления. Выгрузка содержит полные адреса, включая токены подписок.

Имена чувствительны к регистру: 1–64 латинские буквы, цифры, `_` или `-`. Назначение — до 8192 байт после URL-кодирования. Общий JSON ограничен 8 МиБ. Сервис читает его один раз при старте и последовательно сохраняет изменения через временный файл и атомарное переименование. При ошибке записи прежние данные остаются в памяти; повреждённый файл при запуске не перезаписывается. Запускайте только один процесс на файл.

После установки скриптом файл находится **вне репозитория**, в `/var/lib/subs-resolver-links/links.json`, и сохраняется при обновлениях. При самостоятельном запуске используется `./data/short-links.json`; путь можно задать через `SHORT_LINKS_FILE`.

Для переноса через браузер:

1. На старом сервере откройте основную страницу → «Перенос данных» → «Скачать JSON».
2. Разверните сервис на новом сервере обычной командой установки с его доменом.
3. На новом сервере откройте страницу с его UUID → «Перенос данных», выберите JSON и нажмите «Загрузить JSON».
4. Подтвердите полную замену списка. Импорт проверяет все записи и сохраняет весь файл атомарно; при неверном формате или ошибке записи старые данные остаются. Новые ссылки работают сразу, без перезапуска.

Импорт принимает выгрузки формата `{"version":1,"links":{"ABC":"https://example.com/"}}` до 8 МиБ. Пустой объект `links` очищает список. Импорт заменяет, а не объединяет записи. Доступен только через страницу с UUID; домен и UUID сервиса из JSON не меняются. При обрыве связи во время загрузки скачайте JSON с сервера и проверьте результат перед повторной попыткой.

Альтернатива через SSH: загрузите скачанный JSON на сервер, затем выполните (путь `/tmp/short-links.json` замените при необходимости):

```bash
sudo systemctl stop subs-resolver
sudo install -o subs-resolver -g subs-resolver -m 600 /tmp/short-links.json /var/lib/subs-resolver-links/links.json
sudo systemctl start subs-resolver
```

Восстановление заменяет весь список. Для сохранения прежних коротких URL новый сервер должен обслуживать тот же домен. Если назначение содержит ссылку на старый домен или `ACCESS_ID`, сохраните их либо измените назначение через форму.

Обновление на Ubuntu / Debian выполняется той же командой установки:

```bash
curl -fsSL https://raw.githubusercontent.com/Dmitriy129/subs-resolver/main/scripts/deploy.sh | sudo bash -s -- --domain YOUR_DOMAIN
```

У fallback-ссылки нет общего браузерного лимита ровно 2000 символов. Node по умолчанию ограничивает запросный URL и HTTP-заголовки общим размером около 16 КиБ; у клиента и прокси могут быть свои ограничения. При подсчёте учитывайте URL-кодирование и повторяющиеся `subs=`.
